## 任务四：最可能问的 20 个问题和最容易背的答案

### 1. 怎么根据需求文档设计测试点？

先拆业务流程、角色权限、输入输出、边界和异常，再补充数据准备和回归范围。比如我的接口项目会按 CRUD、分页、非法参数、未知 id 拆测试点。

### 2. 怎么写测试用例？

我会先明确测试目标，再写前置条件、步骤、测试数据和预期结果。项目里我会把正常创建、重复数据、非法参数、查询校验分别写成可回归用例。

### 3. 测试用例包含哪些要素？

一般包括用例编号、标题、优先级、前置条件、测试数据、操作步骤、预期结果和实际结果。接口用例还会写请求方法、路径、参数和断言。

### 4. 功能测试、接口测试、自动化测试、回归测试有什么区别？

功能测试看业务是否符合需求；接口测试看服务输入输出；自动化是用脚本重复执行；回归测试是验证修改没有破坏旧功能。我的项目主要做接口自动化回归。

### 5. 你怎么测试一个新增/修改/删除接口？

先看接口文档，再测正常参数、必填缺失、非法类型、边界值、重复请求和数据库结果。我的图书项目会校验状态码、响应字段和数据库记录。

### 6. 接口测试一般校验什么？

校验状态码、响应结构、字段类型、错误码、业务数据、权限、幂等性和数据库一致性。我做接口自动化时会把响应断言和 SQL 校验结合起来。

### 7. pytest 用过哪些功能？

我用过参数化、fixture、marker、断言、测试目录组织和 CI 执行。比如用 marker 区分 smoke、regression、db，用参数化覆盖多组异常参数。

### 8. requests 怎么发请求？

用 requests.get、post、put、delete 发请求，传 params、json、headers，再读取 status_code 和 json 响应做断言。项目里我封装过 RequestClient 复用请求逻辑。

### 9. Postman 和自动化脚本区别？

Postman 适合调试和手工验证接口，脚本更适合批量执行、持续回归和接入 CI。我的项目把稳定接口场景沉淀成 pytest 用例，减少重复手工测试。

### 10. SQL 在测试里怎么用？

SQL 主要用来准备数据、清理数据、查询落库结果和校验数据一致性。比如创建图书后，我会查数据库确认记录是否真的新增且字段正确。

### 11. 数据库一致性怎么校验？

接口返回成功不一定代表数据正确，所以要查数据库确认新增、修改、删除后的状态。我的接口项目会对创建、更新、删除后的记录做一致性校验。

### 12. 发现 bug 后怎么提交和跟踪？

我会写清环境、步骤、测试数据、实际结果、预期结果、截图或日志、严重程度。修复后按原步骤复现，再补回归用例，确认问题闭环。

### 13. 怎么判断 bug 严重程度和优先级？

严重程度看影响范围和后果，比如阻塞流程、数据错误、崩溃；优先级看修复紧急程度。企业系统里数据错误和核心流程阻塞通常优先级高。

### 14. 回归测试怎么做？

先确定改动范围和受影响模块，再选核心主流程、历史 bug、相关接口和高风险场景执行。我的 MVP 会把 Badcase Replay 作为回归入口之一。

### 15. 冒烟测试怎么做？

冒烟测试先验证版本是否具备继续测试的基本条件，覆盖登录、核心接口、主流程和关键页面。接口项目里我会用 smoke marker 跑最核心的接口。

### 16. 性能测试了解多少？

我了解基础指标，比如响应时间、并发数、吞吐量、错误率和资源占用。现在还偏基础，能协助做压测执行、数据记录和超时问题初步分析。

### 17. 兼容性测试怎么做？

先确定支持的浏览器、系统、分辨率或环境版本，再覆盖核心流程和高风险页面。企业产品还要关注不同环境配置下接口和数据表现是否一致。

### 18. 你项目里最能体现测试开发能力的地方是什么？

最能体现的是把接口场景沉淀成 pytest 自动化回归，并接入 CI。MVP 项目里也把评测样本、自动评分、Badcase Replay 串成了质量闭环。

### 19. 你这个大模型评测项目和软件测试岗位有什么关系？

我不会把它当算法项目讲。它更像质量评测平台：准备样本、自动执行、生成报告、沉淀 Badcase、Replay 回归，这和软件测试闭环是相通的。

### 20. 你在项目中遇到的最大困难是什么？

最大困难是怎么让失败结果可复现、可分析。后来我把 Badcase 结构化保存，并做查询、详情、Replay 和 Export，让问题能沉淀成回归资产。

## 任务五：把 MVP 项目改成适合这个岗位的讲法

### 1. 30 秒版项目介绍

这个项目我会把它定位成一个“质量评测和自动化回归平台 MVP”。它用 FastAPI 提供评测接口，准备了 50 条 JSONL 样本，通过 runner 批量执行并自动评分，生成 latest_report.json。对于失败结果，会沉淀成 Badcase，支持查询、详情、Replay 和 Export，最后用 pytest 和 GitHub Actions 做回归验证。

### 2. 1 分钟版项目介绍

这个 MVP 表面上是面向 LLM/RAG/Agent 应用，但我重点做的是质量评测闭环。项目里有一个 `/api/v1/eval/ask` 问答评测接口，配了 50 条 JSONL 评测样本，通过 eval runner 批量执行，metrics 自动评分，并输出 latest_report.json 结构化报告。

对不符合预期的结果，我没有只停留在“看一下失败”，而是沉淀成 17 条 Badcase，保存到 badcases.jsonl，并支持查询、详情、Replay 和 Export。这样失败样本可以复现，也可以进入回归。最后我用 pytest 做参数化回归，并接入 GitHub Actions，当前本地 pytest 是 162 passed，1 skipped，CI 已通过。

### 3. 3 分钟版项目介绍

这个项目我面试测试岗位时会按“质量评测平台”来讲，而不是按 AI 算法项目讲。

项目背景是 LLM/RAG/Agent 类应用输出不稳定，单靠人工体验很难判断一次迭代有没有质量退化。所以我做了一个 MVP，把评测过程拆成测试数据、执行入口、评分规则、报告输出、Badcase 沉淀和回归验证几个部分。

第一部分是测试执行。后端用 FastAPI，提供 `/api/v1/eval/ask` 问答评测接口；测试数据用 50 条 JSONL 样本保存，便于批量执行和版本管理；eval runner 会读取样本批量请求接口，再用 metrics 做自动评分，最后输出 latest_report.json。这个报告里可以看整体通过率、失败样本和评分明细。

第二部分是 Badcase 闭环。对于不符合预期的样本，我把它们结构化保存为 badcases.jsonl，目前有 17 条。平台支持 Badcase 查询、详情、Replay 和 Export。Replay 的意义是让失败场景能复现，而不是只存在一次运行日志里；Export 的意义是方便后续复盘、交接或者加入回归集合。

第三部分是自动化回归。我用 pytest 做参数化回归，把核心评测逻辑、Badcase 流程和 Agent 工具调用评测纳入测试，并接入 GitHub Actions。现在本地测试结果是 162 passed，1 skipped，CI 已通过。

如果放到用友这个岗位上，我认为它对应的不是模型能力，而是测试思维：固定测试数据、自动执行、结构化报告、缺陷样本沉淀、复现验证和持续回归。企业级业务产品也可以用类似思路，把核心业务流程、接口契约、历史缺陷和高风险场景沉淀成可持续执行的回归资产。

### 4. 追问“这个项目是不是偏 AI，和软件测试有什么关系”

确实项目对象是 AI 应用，但我做的重点不是训练模型，而是质量评测流程。里面的样本集对应测试数据，runner 对应自动化执行，metrics 对应断言和评分，latest_report 对应测试报告，Badcase Replay 对应缺陷复现和回归。所以它和软件测试岗位的关系在于质量闭环，而不是算法本身。

### 5. 追问“哪些是你自己做的”

我主要负责后端评测接口、JSONL 评测样本组织、metrics 自动评分、批量 runner、latest_report.json 报告、Badcase 的查询/详情/Replay/Export，以及 pytest 参数化回归和 GitHub Actions CI。我的重点是把评测流程做成可重复、可回归、可追踪。

### 6. 追问“为什么用 deterministic mock”

因为这个 MVP 的目标是验证评测流程和回归机制，不是比较真实模型效果。真实模型输出有随机性，会让测试结果不稳定。deterministic mock 可以保证同一输入得到稳定输出，方便验证评分逻辑、Badcase 复现和 CI 回归。

### 7. 追问“pass_rate=0.66 和 17 条 badcase 说明什么”

它说明当前样本集下还有一部分场景没有达到预期，不能只看接口可用，还要看回答质量是否符合标准。17 条 Badcase 的价值是把失败样本沉淀下来，后续可以分析失败原因、调整规则或实现，并作为回归用例防止同类问题反复出现。

### 8. 追问“这个项目还有哪些不足”

第一，样本量还比较小，只有 50 条，覆盖场景还不够企业级。第二，评分规则偏 MVP，还没有人工复核和多维权重。第三，Badcase 分类还可以更细，比如按原因、模块、严重程度统计。第四，性能测试和多环境兼容还只是基础，没有做完整压测。

### 3. 必背测试八股

1. 测试用例要素：编号、标题、优先级、前置条件、测试数据、步骤、预期结果、实际结果。
