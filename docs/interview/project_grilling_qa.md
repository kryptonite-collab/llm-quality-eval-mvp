# llm-quality-eval-mvp 测试/测开面试拷打问答

这份文档只针对 `llm-quality-eval-mvp` 项目本身，用测试/测开实习岗面试官连续追问的方式，帮助面试时把项目讲清楚。回答风格按学生口述来写，重点是清楚、直接、不过度包装。

## 一、项目核心问题拷打问答

### 1. 这个项目到底是干什么的？

**面试官追问**

你这个项目到底是干什么的？是聊天机器人吗？

**推荐回答**

不是聊天机器人，也不是完整 Web 平台。这个项目是一个轻量级 LLM 质量评测工具链，主要形式是 **CLI，加上 JSON 和 Markdown 报告**。它的目标是把大模型应用的回答质量，从人工看几条结果，变成可以重复执行、可以对比、可以回归检查的工程流程。

**面试官继续追问**

那它和普通调用大模型 API 有什么区别？

**继续追问回答**

普通调用 API 只是拿到一次回答，这个项目关心的是**一批测试用例的整体质量**，比如通过率、badcase 数量、关键证据、延迟、Prompt A/B 对比结果。它更像测试工具，不是应用入口。

### 2. 你自己具体做了什么？

**面试官追问**

你在这个项目里具体负责了什么？不要泛泛说参与项目。

**推荐回答**

我主要做的是围绕 LLM 评测流程的工程化部分：设计最小评测数据、接入 deterministic/mock provider 保证测试稳定、接入 DeepSeek 的 OpenAI-compatible Provider、设计 JSON 和 Markdown 报告输出，以及做 Prompt A/B 对比和报告质量门禁。整体目标是让一次评测能被记录、被比较、被复跑。

**面试官继续追问**

你觉得最能体现你工作的点是哪一个？

**继续追问回答**

我觉得是把真实模型调用和自动化测试分开。普通 pytest 和 CI 用 mock provider 保证稳定，真实 DeepSeek 评测需要本机 `.env` 手动注入 Key 后运行。这样既能展示真实模型接入能力，又不会让 CI 因网络、额度、模型波动而不稳定。

### 3. 接入了什么真实大模型？

**面试官追问**

你这个项目接入了什么真实大模型？

**推荐回答**

项目接入的是 DeepSeek 的 OpenAI-compatible Provider。也就是说，它通过兼容 OpenAI 风格的接口调用 DeepSeek，而不是只写了一个 mock。

**面试官继续追问**

那默认运行会调用 DeepSeek 吗？

**继续追问回答**

不会。默认使用 deterministic/mock provider，普通 pytest 和 GitHub Actions 都不调用真实 DeepSeek。真实 DeepSeek 评测需要本机准备 `.env`，再用类似 `uv --env-file .env ...` 的方式手动运行。

### 4. 为什么真实模型不进 pytest / CI？

**面试官追问**

为什么不把真实 DeepSeek 放进 pytest 和 CI？这样不是更真实吗？

**推荐回答**

真实是更真实，但不适合直接放进普通 pytest 和 CI。因为真实模型调用会受网络、API Key、额度、限流、模型版本和随机性影响，导致测试结果不稳定。CI 的核心要求是稳定、可复现、可快速定位问题，所以普通 CI 只跑 mock provider 和报告检查。

**面试官继续追问**

那真实模型评测还有意义吗？

**继续追问回答**

有意义，但它应该作为手动或受控环境下的评测任务，而不是每次提交都跑。项目把真实评测和 CI 稳定性分开，是一个工程取舍：日常回归稳定，真实质量验证按需执行。

### 5. 为什么要做 mock provider？

**面试官追问**

为什么要做 mock provider？是不是因为没有真正接入模型？

**推荐回答**

不是。mock provider 的作用是保证自动化测试稳定。LLM 输出天然可能波动，如果 pytest 每次都请求真实模型，测试很难稳定通过。mock provider 用确定性的返回结果验证评测流程本身，比如数据读取、指标计算、报告生成、质量门禁这些逻辑。

**面试官继续追问**

mock 会不会导致测不到真实问题？

**继续追问回答**

会有这个限制，所以项目同时保留 DeepSeek 真实 provider。mock 负责工程流程的稳定回归，真实 provider 负责按需验证模型效果。两者不是互相替代，而是分层使用。

### 6. 这个项目有什么实际价值？

**面试官追问**

这个项目实际价值是什么？听起来只是跑几条测试数据。

**推荐回答**

它的实际价值是把 LLM 应用质量从人工观察变成工程流程。比如以前改了 prompt，只能肉眼看几条回答觉得好不好；现在可以用同一份数据集跑 baseline 和 improved，输出通过率、badcase、延迟和 case-level evidence，判断改动到底有没有提升，有没有引入回退。

**面试官继续追问**

如果数据集很小，价值是不是有限？

**继续追问回答**

是的，数据集小会限制覆盖面，所以这个项目定位是 MVP。它先把流程跑通：数据集、provider、指标、报告、门禁。后续可以扩充数据集和指标，但核心价值是先建立可复现的评测闭环。

### 7. 为什么没有网页？

**面试官追问**

为什么没有做网页？是不是项目不完整？

**推荐回答**

这个项目的定位不是完整 Web 平台，而是轻量级评测工具链。对测试/测开场景来说，CLI、JSON、Markdown 报告已经能满足自动化运行、版本管理、CI 检查和结果追踪。没有网页是范围控制，不是没有价值。

**面试官继续追问**

那如果给业务同学用，没有网页会不会不方便？

**继续追问回答**

会有一定门槛。如果后续面向更多非技术用户，可以加一个简单的 Web Dashboard。但当前阶段优先做可复现评测和报告产物，比先做界面更符合测试工具的 MVP 目标。

### 8. 怎么判断模型回答质量？

**面试官追问**

你们怎么判断模型回答质量？是不是人工主观判断？

**推荐回答**

项目用轻量指标做自动化判断，包括 keyword recall、source_hit、refusal_when_answer_expected、pass rate、badcase count、latency 和 case-level evidence。它不是完整 LLM-as-Judge，而是用明确、可解释的规则先覆盖最关键的质量风险。

**面试官继续追问**

这些指标够准确吗？

**继续追问回答**

不敢说完全准确。它们是轻量指标，优点是稳定、便宜、可解释；缺点是不能完全理解语义。所以项目会把 case-level evidence 输出出来，方便人工复核 badcase。

### 9. keyword recall 有什么局限？

**面试官追问**

keyword recall 是不是太简单了？模型换个说法不就误判了吗？

**推荐回答**

是的，这是它的局限。keyword recall 主要看回答里有没有覆盖预期关键词，优点是简单稳定，缺点是对同义表达、语义正确但没命中关键词的情况不够友好，也可能出现堆关键词但回答质量不高的情况。

**面试官继续追问**

那为什么还要用？

**继续追问回答**

因为这个项目是轻量 MVP，keyword recall 适合做第一层自动化质量信号。它不是最终裁判，而是帮助快速发现明显缺失的信息。更复杂的语义评估可以作为后续增强。

### 10. source_hit 是什么？

**面试官追问**

source_hit 是什么指标？

**推荐回答**

source_hit 用来判断模型回答是否命中了预期来源或证据。对于 RAG 类问题，答案不只是要看起来对，还要能对应到给定材料，比如 `policy_sample.md` 里的政策内容。source_hit 就是检查回答是否和指定来源相关。

**面试官继续追问**

它解决什么问题？

**继续追问回答**

它主要解决“模型凭空回答”的风险。即使答案文字看起来合理，如果没有基于给定资料，也可能是幻觉。source_hit 能帮助判断回答是否真的贴近检索材料。

### 11. refusal_when_answer_expected 是什么？

**面试官追问**

refusal_when_answer_expected 是什么？

**推荐回答**

它表示在本来应该回答的问题上，模型却拒答了。比如问题是根据给定政策材料回答，材料里明明有答案，但模型说“无法回答”或“没有相关信息”，这就是一种质量问题。

**面试官继续追问**

为什么要单独统计这个？

**继续追问回答**

因为在真实业务里，模型不该乱答，但也不能过度保守。拒答率太高会影响可用性。这个指标能帮助发现 prompt 或检索上下文导致的过度拒答问题。

### 12. Prompt A/B 评测怎么做？

**面试官追问**

Prompt A/B 评测在你这个项目里怎么做？

**推荐回答**

项目用同一份数据集分别跑 baseline prompt 和 improved RAG prompt，然后分别生成结果，再输出 JSON 和 Markdown compare report。对比内容包括通过率、badcase、延迟、case-level evidence，以及哪些 case 提升或回退。

**面试官继续追问**

为什么必须用同一份数据集？

**继续追问回答**

因为只有数据集相同，A/B 的结果才可比。如果 baseline 和 improved 跑的是不同 case，就没法判断差异是 prompt 带来的，还是数据本身不同带来的。

### 13. baseline prompt 和 improved prompt 有什么区别？

**面试官追问**

baseline prompt 和 improved prompt 有什么区别？

**推荐回答**

baseline prompt 更像基础版本，主要让模型回答问题。improved RAG prompt 会更强调基于给定资料回答、覆盖关键信息、避免无依据扩展，并在没有证据时更谨慎。它的目标是提高 RAG 场景下的稳定性和可解释性。

**面试官继续追问**

那 improved 一定更好吗？

**继续追问回答**

不一定。improved 可能提高通过率，也可能带来更高延迟，或者在某些 case 上更保守。所以项目不是只看一个样例，而是用 A/B 报告看整体通过率和 regressed cases。

### 14. real_rag_sample.jsonl 怎么设计？

**面试官追问**

`real_rag_sample.jsonl` 是怎么设计的？

**推荐回答**

它是最小真实 RAG 评测数据集，每一行是一条 case。它会包含问题、期望关键词、期望来源或证据相关信息，用来验证模型能不能基于给定 policy 文档回答，而不是随便生成。

**面试官继续追问**

为什么用 jsonl？

**继续追问回答**

jsonl 适合测试数据集扩展，一行一个 case，便于追加、版本管理和逐条定位问题。某个 case 出问题时，也容易在报告里对应到具体输入和证据。

### 15. policy_sample.md 是什么？

**面试官追问**

`policy_sample.md` 是什么？

**推荐回答**

它是项目里的最小政策类样本文档，用来模拟真实 RAG 场景里的知识来源。评测时问题应该基于这份文档回答，指标会检查回答是否覆盖关键点、是否命中来源、是否出现不该拒答的情况。

**面试官继续追问**

为什么用政策类文档？

**继续追问回答**

因为政策类问题比较适合做可验证评测。答案通常有明确依据，不能随便编，也适合测试模型是否能按材料回答。

### 16. Badcase 是什么，怎么处理？

**面试官追问**

Badcase 是什么？

**推荐回答**

Badcase 就是没有通过评测规则的 case，比如关键词没覆盖、没有命中来源、应该回答却拒答，或者相比 baseline 出现回退。它代表需要重点分析的失败样本。

**面试官继续追问**

发现 badcase 后你怎么处理？

**继续追问回答**

我会先看 case-level evidence，确认失败原因，是数据设计问题、prompt 问题、指标误判，还是模型能力问题。然后再决定是修 prompt、补充数据、调整指标，还是把它记录为已知限制。

### 17. case-level evidence 有什么用？

**面试官追问**

case-level evidence 有什么用？

**推荐回答**

它的作用是让每个 case 的判断有依据，不只是给一个 pass 或 fail。比如可以看到模型回答、命中的关键词、缺失的关键词、来源命中情况、延迟等。这样 badcase 才能被复盘。

**面试官继续追问**

为什么不只看总通过率？

**继续追问回答**

总通过率只能说明整体趋势，不能解释为什么失败。测试开发不能只给一个分数，还要能定位问题。case-level evidence 就是为了定位和复盘。

### 18. check_eval_report.py 有什么用？

**面试官追问**

`check_eval_report.py` 有什么用？

**推荐回答**

它是报告质量门禁脚本，只读取已有评测报告，检查报告是否达到预期要求，比如通过率、badcase 数量或关键字段。它不调用真实模型。

**面试官继续追问**

为什么它不直接跑模型？

**继续追问回答**

因为它的职责是检查已有报告，而不是执行评测。这样它可以稳定地放在自动化流程里，不受真实模型网络和 Key 的影响。职责拆开后，流程更清楚。

### 19. 这个项目怎么体现测试开发能力？

**面试官追问**

这个项目怎么体现测试开发能力，而不是只是写脚本？

**推荐回答**

它体现的是把一个不稳定的 LLM 输出，转成可测试、可回归、可对比的流程。里面有测试数据设计、mock 隔离、真实 provider 接入、指标设计、报告生成、质量门禁和 CI 稳定性考虑。这些都是测试开发会关注的工程问题。

**面试官继续追问**

你觉得和普通测试最大的不同是什么？

**继续追问回答**

普通测试很多时候断言是确定的，但 LLM 评测的输出更开放。所以这里不能只写 equals 断言，要设计更适合 LLM 的质量信号，比如关键词覆盖、来源命中、拒答检测和 badcase 分析。

### 20. 这个项目和普通 pytest 有什么区别？

**面试官追问**

这个项目和普通 pytest 有什么区别？

**推荐回答**

pytest 更偏代码逻辑正确性验证，比如函数输入输出是否符合预期。这个项目除了 pytest，还关注模型回答质量的批量评测，比如 prompt 改动后质量有没有提升、有没有回退、报告是否能用于复盘。

**面试官继续追问**

那 pytest 在项目里还有什么作用？

**继续追问回答**

pytest 主要保证评测工具链本身可靠，比如数据解析、mock provider、指标计算、报告生成这些逻辑不坏。真实模型效果则通过单独的评测命令和报告来观察。

### 21. 怎么保证评测结果可复现？

**面试官追问**

你怎么保证评测结果可复现？

**推荐回答**

首先普通自动化测试默认用 deterministic/mock provider，输出是确定的。其次 Prompt A/B 使用同一份数据集。再次，评测结果会落到 JSON 和 Markdown 报告里，可以保留证据。真实模型部分虽然不能完全保证复现，但通过固定数据、固定 prompt、记录报告，可以尽量降低不确定性。

**面试官继续追问**

真实模型还是会变，那怎么办？

**继续追问回答**

所以真实模型不作为普通 CI 的硬依赖。真实评测结果更多用于人工分析和阶段性对比。CI 里保留稳定的 mock 和报告检查，保证工程链路不被模型波动影响。

### 22. improved prompt 通过率更高但延迟更高时怎么取舍？

**面试官追问**

如果 improved prompt 通过率更高，但延迟更高，你怎么取舍？

**推荐回答**

我不会只看通过率，也不会只看延迟，要结合业务目标。如果是对准确性要求高的场景，可以接受一定延迟换质量；如果是实时交互场景，就要设延迟上限。项目报告里同时输出 pass rate 和 latency，就是为了支持这种取舍。

**面试官继续追问**

那你会怎么给结论？

**继续追问回答**

我会说 improved 在质量上有提升，但需要看延迟成本是否在可接受范围内。如果通过率提升明显、badcase 减少明显，而且延迟没有超过业务阈值，就可以考虑采用；否则需要继续优化 prompt。

### 23. 出现 regressed cases 怎么办？

**面试官追问**

Prompt A/B 里出现 regressed cases 怎么办？

**推荐回答**

regressed cases 是重点分析对象。说明 improved prompt 虽然可能整体更好，但在某些样本上变差了。我会逐条看 evidence，判断是 prompt 过度约束、关键词设计不合理，还是模型对某类问题处理变差。

**面试官继续追问**

如果整体通过率提升，但有少数回退，还能上线吗？

**继续追问回答**

要看回退 case 的严重程度。如果回退的是核心业务问题，不能只看整体通过率。如果只是低风险边缘问题，可以记录并继续优化。测试报告的价值就是让这个决策有依据。

### 24. 这个项目是不是只是调 API？

**面试官追问**

这个项目是不是只是调 API？

**推荐回答**

不是。调 API 只是 provider 的一部分。项目更核心的是评测流程：数据集怎么设计、结果怎么量化、badcase 怎么暴露、报告怎么对比、CI 怎么稳定、真实模型怎么和自动化测试隔离。

**面试官继续追问**

那如果没有 DeepSeek 接入，这项目还有价值吗？

**继续追问回答**

有一部分价值，因为 mock provider 可以验证评测链路。但真实 provider 能证明这套流程可以连接真实模型，所以两者结合更完整。

### 25. 为什么不用完整 RAGAS？

**面试官追问**

为什么不用完整 RAGAS 这类框架？

**推荐回答**

因为这个项目定位是轻量 MVP，不是完整 RAGAS 平台。完整 RAGAS 能做更丰富的语义评估，但引入成本、依赖复杂度和解释成本也更高。当前项目先做可控、可解释、容易跑通的轻量指标。

**面试官继续追问**

那是不是说明评测能力不够专业？

**继续追问回答**

不是不专业，而是阶段不同。MVP 阶段先建立评测闭环，保证测试数据、报告、对比、门禁能跑起来。后续如果业务需要更复杂的语义评估，可以再接 RAGAS 或 LLM-as-Judge。

### 26. 为什么没有接完整向量数据库 / 完整 RAG？

**面试官追问**

为什么没有接完整向量数据库或完整 RAG？

**推荐回答**

因为项目重点不是实现一个完整 RAG 系统，而是评测 LLM/RAG 回答质量。`policy_sample.md` 和 `real_rag_sample.jsonl` 已经能构造最小真实 RAG 评测案例。先不接向量数据库，可以减少变量，更专注在评测流程本身。

**面试官继续追问**

那没有向量库，RAG 评测真实吗？

**继续追问回答**

它是最小真实案例，不是完整生产 RAG。它可以验证基于资料回答、来源命中、拒答等关键质量点。但如果要模拟生产环境，下一步可以接检索层和向量库。

### 27. 项目最大不足是什么？

**面试官追问**

你觉得项目最大不足是什么？

**推荐回答**

最大不足是评测指标还比较轻量，数据集规模也小，还没有完整 LLM-as-Judge、完整 RAGAS、完整 Web Dashboard 或生产级 RAG 检索链路。所以它更适合作为 MVP 和测试开发能力展示，而不是成熟评测平台。

**面试官继续追问**

那你为什么还认为它值得做？

**继续追问回答**

因为它解决了一个很实际的起点问题：怎么把 prompt 改动和模型回答质量变成可复现、可对比、可回归的流程。很多团队一开始缺的就是这个闭环，而不是一上来就做大平台。

### 28. 如果继续完善，下一步做什么？

**面试官追问**

如果继续完善，你下一步做什么？

**推荐回答**

我会优先扩充评测数据集，增加更多真实业务 case 和边界 case；其次完善指标，比如加入更好的语义相似度或 LLM-as-Judge；再往后可以接入检索层、向量数据库和简单 Dashboard，让报告更适合多人查看。

**面试官继续追问**

为什么不是先做网页？

**继续追问回答**

因为网页主要提升展示体验，但如果底层数据集和指标不够扎实，网页只是把不稳定结果展示出来。测试工具应该先保证评测逻辑可靠，再考虑展示层。

### 29. 从这个项目学到了什么？

**面试官追问**

你从这个项目学到了什么？

**推荐回答**

我学到 LLM 应用测试不能只靠人工体验，也不能简单套传统断言。要把不确定的模型输出拆成可观测指标，比如关键词覆盖、来源命中、拒答、延迟和 badcase，再用报告和门禁让它进入工程流程。

**面试官继续追问**

这对测试开发岗位有什么帮助？

**继续追问回答**

测试开发岗位不只是写测试用例，还要建设测试工具和质量平台。这个项目让我练习了 mock 隔离、CI 稳定性、测试数据设计、质量指标设计和报告自动化，这些都和测开工作很相关。

## 二、10 组连续追问模拟

### 模拟 1：项目价值

**面试官追问**

你这个项目解决了什么真实问题？

**推荐回答**

它解决的是 LLM 应用质量难以稳定评估的问题。以前改 prompt 后只能人工看几条输出，现在可以用同一份数据集跑评测，产出通过率、badcase、延迟和证据。

**面试官继续追问**

如果只是小样本，怎么证明有价值？

**继续追问回答**

小样本不能证明覆盖充分，但能证明评测流程成立。这个项目是 MVP，先把数据、指标、报告、对比和门禁打通，后续再扩大样本。

**面试官追问**

这对团队有什么帮助？

**推荐回答**

团队可以在改 prompt 或换模型后快速知道质量有没有变化，不用完全靠主观感觉。尤其是 badcase 和回退样本能帮助定位问题。

**面试官继续追问**

一句话总结价值？

**继续追问回答**

把 LLM 质量评估从人工观察，变成可复现、可对比、可回归的工程流程。

### 模拟 2：真实模型接入

**面试官追问**

你接入真实模型了吗？

**推荐回答**

接入了 DeepSeek 的 OpenAI-compatible Provider，但默认不调用真实模型。

**面试官继续追问**

为什么默认不调用？

**继续追问回答**

因为真实调用依赖 API Key、网络和额度，也可能受模型输出波动影响。默认用 mock provider 才能保证 pytest 和 CI 稳定。

**面试官追问**

那怎么运行真实评测？

**推荐回答**

需要本机准备 `.env`，手动注入 API Key，然后通过 `uv --env-file .env ...` 这类命令运行真实评测。

**面试官继续追问**

你会把 Key 提交到仓库吗？

**继续追问回答**

不会。API Key 只放本机环境，不进代码、不进报告、不进 GitHub。

### 模拟 3：Prompt A/B

**面试官追问**

你怎么做 Prompt A/B？

**推荐回答**

用同一份 `real_rag_sample.jsonl` 分别跑 baseline prompt 和 improved RAG prompt，然后生成 compare report。

**面试官继续追问**

看哪些对比项？

**继续追问回答**

看 pass rate、badcase count、latency、case-level evidence，以及哪些 case improved，哪些 case regressed。

**面试官追问**

为什么不只看平均分？

**推荐回答**

平均分会掩盖具体失败样本。测试开发更关心能不能定位问题，所以必须看 case-level evidence。

**面试官继续追问**

如果 improved 整体更好但有回退呢？

**继续追问回答**

要看回退样本严重程度。核心业务 case 回退就不能轻易采用，低风险 case 可以记录后继续优化。

### 模拟 4：指标设计

**面试官追问**

你们有哪些指标？

**推荐回答**

主要有 keyword recall、source_hit、refusal_when_answer_expected、pass rate、badcase count、latency 和 case-level evidence。

**面试官继续追问**

这些指标是不是太轻量？

**继续追问回答**

是轻量指标，但这是有意取舍。它们稳定、便宜、容易解释，适合作为 MVP 的第一层评测。

**面试官追问**

keyword recall 最大问题是什么？

**推荐回答**

它不理解深层语义，可能漏判同义表达，也可能被堆关键词误导。

**面试官继续追问**

那后续怎么增强？

**继续追问回答**

可以加入语义相似度、LLM-as-Judge 或 RAGAS 类指标，但要注意成本、稳定性和可解释性。

### 模拟 5：Badcase

**面试官追问**

Badcase 在项目里怎么定义？

**推荐回答**

没有通过评测规则的 case 就是 badcase，比如关键词缺失、来源没命中、应该回答却拒答，或者 A/B 对比里出现回退。

**面试官继续追问**

发现 badcase 后第一步做什么？

**继续追问回答**

先看 case-level evidence，确认失败原因，而不是马上改 prompt。

**面试官追问**

可能有哪些原因？

**推荐回答**

可能是 prompt 不清楚、数据集预期不合理、指标误判，也可能是真实模型能力不足。

**面试官继续追问**

怎么避免同类问题再次出现？

**继续追问回答**

把典型 badcase 固化进数据集，后续每次评测都跑，形成回归测试。

### 模拟 6：mock 和 CI

**面试官追问**

为什么 CI 不跑真实 DeepSeek？

**推荐回答**

CI 要稳定，真实模型调用会受网络、Key、额度、限流和模型波动影响，不适合作为每次提交的硬依赖。

**面试官继续追问**

那 CI 还能测到什么？

**继续追问回答**

CI 可以测评测工具链本身，比如数据解析、指标计算、报告生成、mock provider 和报告门禁。

**面试官追问**

mock 会不会太假？

**推荐回答**

mock 不是用来证明模型质量，而是用来证明工程链路稳定。真实模型评测单独手动跑。

**面试官继续追问**

这体现什么测试思想？

**继续追问回答**

体现测试分层。稳定链路进 CI，不稳定外部依赖放到受控环境运行。

没有网页会不会影响展示？

## 三、最容易被拷打的 15 个问题速背版

1. **这个项目一句话是什么？**
   一个轻量级 LLM 质量评测工具链，用 CLI 跑评测，输出 JSON/Markdown 报告，帮助比较 prompt 或模型改动前后的质量。

2. **它是不是聊天机器人？**
   不是。它不负责聊天交互，负责评测模型回答质量。

3. **它是不是完整 RAGAS 平台？**
   不是。它是轻量 MVP，用可解释的规则指标先建立评测闭环。

4. **接入了什么真实模型？**
   接入了 DeepSeek OpenAI-compatible Provider。

5. **默认会不会调用真实 DeepSeek？**
   不会。默认用 deterministic/mock provider，真实评测需要本机 `.env` 手动注入 Key 后运行。

6. **为什么真实 DeepSeek 不进 CI？**
   因为真实调用受网络、Key、额度、限流和模型波动影响，会破坏 CI 稳定性。

7. **mock provider 的意义是什么？**
   保证 pytest 和 CI 可以稳定验证评测链路本身。

8. **怎么判断回答质量？**
   用 keyword recall、source_hit、refusal_when_answer_expected、pass rate、badcase count、latency 和 case-level evidence。

9. **keyword recall 的局限是什么？**
   它不理解深层语义，可能漏判同义表达，也可能被堆关键词误导。

10. **source_hit 解决什么问题？**
    检查回答是否基于预期来源，降低模型凭空回答的风险。

11. **refusal_when_answer_expected 是什么？**
    本来应该回答的问题，模型却拒答，这是可用性问题。

12. **Prompt A/B 怎么做？**
    同一份数据集分别跑 baseline prompt 和 improved RAG prompt，再生成 compare report。

13. **Badcase 怎么处理？**
    先看 case-level evidence 定位原因，再决定改 prompt、改数据、调指标或记录限制。

14. **为什么没有网页？**
    因为项目定位是轻量测试工具链，CLI 和 Markdown 报告更适合自动化和 CI；网页是后续增强。

15. **项目最大不足是什么？**
    数据集小、指标轻量、没有完整 RAGAS/LLM-as-Judge/向量库/Web 平台，但作为 MVP 已经打通可复现评测闭环。
